    Research Notes and References

    中文

    This is a design bibliography, not a claim that myVMP copies any product or source. The project implements its own C++ architecture, IR, bytecode, runtimes and ELF transformation. References were used to understand established designs, attacker workflows, ABI rules and measurement pitfalls. License terms of referenced code must be reviewed independently; no external source should be copied without compatible licensing and provenance.

    Virtualization protection and devirtualization

    • SoK: Automatic Deobfuscation of Virtualization-protected Applications — attacker models for recovering fetch/decode/dispatch/handler structure and normalizing VM traces; motivated per-block/profile diversity and honest limits on multi-VM complexity. Paper
    • Matryoshka / process-level nested virtualization — evidence that nesting can raise analysis cost while imposing substantial overhead; motivated sibling VMs before unrestricted recursive nesting. Slides
    • Tigress Virtualize — duplicate instructions, operand-location variation, superoperators, dispatch diversity and reentrant interpreters; informed bounded, testable polymorphism rather than a single opcode permutation. Documentation
    • Recent obfuscation/devirtualization literature reviewed during quality planning — used as prompts for attacker-oriented measurement and evolving VM signatures, not as implementation specifications. arXiv:2601.10261, arXiv:2603.18355, SSRN 5147457, IEEE Access reference

    Open-source virtualization and binary protection

    • VMPacker — ARM64 Linux ELF function virtualization, custom bytecode, opcode randomization, encrypted/reordered bytecode and injection workflow. It reinforced the value of a binary-level frontend and strict module separation. Repository
    • xVMP — LLVM-level virtualization with per-basic-block ideas; informed block identity, block-local crypto domains and quality comparisons while myVMP remains binary-level. Repository
    • binprotect — x64 PE binary virtualization and per-handler layout diversity; useful attacker/implementation reference but not a reusable ARM ELF design. Repository
    • Kiteshield — x86-64 ELF packing and function encryption; informed separation between packing/encryption and semantic VM virtualization. Repository
    • covirt — VM/MBA/self-modifying experiments and documented VM-call failure modes; reinforced the need for an explicit, validated bridge ABI. Repository
    • Miasm — mature lifting and analysis concepts; useful as a future differential oracle, while myVMP retains a compact project-owned IR and no Python runtime dependency. Repository

    Community analyses of commercial protectors, including VMProtect-protected samples, were used to study recognizable dispatcher loops, handler normalization, rolling decode state, operand recovery and trace-based attacks. These analyses motivated changing representation at build, block, instruction and handler levels. myVMP does not claim compatibility with, or reproduction of, VMProtect internals.

    Binary rewriting

    • E9Patch — practical static binary rewriting and placement constraints. Repository, paper
    • LIEF — ELF object model and binary transformation API; useful comparison for segment, section and dynamic-table repair. Repository, ELF API
    • Binary rewriting research on safe patch placement and layout informed fail-closed planning and real-ELF stress tests. DOI 10.1145/3546568, STTT article

    Architecture and ABI standards

    • Arm AArch64 ELF ABI
    • RISC-V unprivileged ISA
    • RISC-V compressed extension
    • RISC-V ELF psABI
    • x86-64 psABI and Intel SDM are preparatory references for a future x86-64 backend.

    Standards, rather than protector writeups, are authoritative for instruction semantics, relocations, calling conventions and ELF behavior.

    Android native platform research

    The long-term Android assessment uses official Android NDK ABI, JNI, native-build, 16 KiB page-size, packaging and signing documentation plus AOSP Bionic linker notes. It concludes that current AArch64 ELF machinery is a strong starting point, but Android support requires a pre-sign NDK .so pipeline and platform-specific compatibility gates. See Android native protection vision for the analysis and sources.

    Testing methodology

    • Csmith informed the optional randomized compiler-output stress layer. Deterministic checked-in fixtures remain primary because failures must be reproducible and minimized.
    • Attacker-oriented review asks whether an analyst can identify a global opcode map, plaintext operand stream, stable block order, uniform handler template or bridge ABI. Each question maps to a measurable diversity or correctness gate.

    Ideas adopted

    1. Function-level binary virtualization with a project-owned IR.
    2. Per-build and per-occurrence physical opcode diversity.
    3. Unified rolling operand encoding across the logical opcode set.
    4. CFG-aware blocks, encrypted key evolution and movable physical layout.
    5. Bounded superoperators and native handler variants.
    6. Explicit sibling-VM ownership and bridge contracts instead of ad-hoc recursion.
    7. Transactional ELF publication and fail-closed validation.
    8. Reproducible manifests plus behavior, diversity, exposure and cost measurement.

    Ideas deliberately deferred or rejected

    • treating high entropy as proof of protection;
    • silently passing unknown native instructions through the VM;
    • unrestricted mutually recursive interpreters without a state/exception ABI;
    • whole-program virtualization as the default deployment model;
    • copying proprietary formats or incompatible open-source implementations.

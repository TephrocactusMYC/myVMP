    Analysis and Reports

    中文

    Report layers

    A useful review combines four kinds of evidence:

    1. Eligibility: ELF/symbol range, relocations and detour plan.
    2. Semantic: lifted IR plus original/protected behavior.
    3. Transformation: profile, block ownership, bridges and encrypted payload metadata.
    4. Quality/cost: byte exposure, diversity, size and runtime ratios.

    No one metric establishes security. In particular, high entropy may merely indicate compression/encryption, and whole-file similarity is dominated by unprotected code.

    Built-in commands

    ./build/myvmp inspect-elf INPUT SYMBOL
./build/myvmp --log-dir DIR protect-dry-run INPUT SYMBOL SEED
./build/myvmp lift-elf-symbol INPUT SYMBOL
./build/myvmp profile-manifest SEED
./build/myvmp quality-report --json BEFORE AFTER

    protect sidecars are JSON and include architecture, VM mode, codecs, profiles, physical blocks, profile owner IDs, successors and bridges. protect-many also produces an aggregate batch manifest.

    For attacker-oriented structural observations, use scripts/vm_attacker_metrics.py:

    python3 scripts/vm_attacker_metrics.py build/protected.elf --output build/attacker.json
python3 scripts/vm_attacker_metrics.py build/a.elf.myvmp.json build/b.elf.myvmp.json
python3 scripts/vm_attacker_metrics.py build/protected.elf --trace build/block-trace.json

    The report covers visible profile fingerprints, manifest CFG/owner/bridge structure, implementation-known operand-format reuse, and optional observed block-trace shape. A trace is a JSON block-ID list or {"block_ids": [...]}. Sidecar graph values measure disclosed metadata; this particular sidecar-oriented tool marks an ELF without a sidecar opaque. That status is a tool limitation, not a claim that the runtime format conceals its structure. These values are structural proxies, not recovered semantics or measured devirtualization effort.

    For an attacker-side runtime bytecode oracle, use scripts/reference_devirtualizer.py:

    python3 scripts/reference_devirtualizer.py build/protected.elf \
  --payload-file-offset 0x123000 --output build/reference-analysis.json
# To ignore an adjacent sidecar, supply the architecture and runtime code size:
python3 scripts/reference_devirtualizer.py build/protected.elf \
  --no-sidecar --architecture aarch64 --runtime-code-size 10024 \
  --payload-file-offset 0x123000 --output build/runtime-only-analysis.json

    The file offset is the payload_offset printed by protect; the runtime code size must match the build being examined (10024 is an example, not a format constant). The tool reads native runtime headers for AArch64, ARM32 and RV64, reverses bytecode whitening and operand-window encoding, and recovers physical blocks, owner indices, logical VM opcodes, operand bytes and explicit static branch targets without a sidecar. It derives additional fallthrough edges from instruction boundaries. AArch64 single-VM opcode mapping uses the patched native dispatcher and the checked-out source's comparison order; the other modes use runtime translation tables. With a sidecar, it compares recovered blocks, owners and CFG edges against published metadata. The v3 report keeps VM instruction/CFG recovery separate from source-level semantic IR recovery, which remains zero; dynamic VM-return edges and handler effects are not inferred. These exposed fields should not be interpreted as evidence of semantic protection. Run make reference-devirtualizer-test with all three cross toolchains to check real protected ELF fixtures, including AArch64 single/sibling mode, truncation and malformed size/target/owner data. Consumers should check schema: payload_file_offset is the runtime start and encrypted_bytecode_file_offset is the encrypted VM region (v1 used the former name for the encrypted region).

    The current integration fixtures produce these exact sidecar comparisons (sibling mode, seeds 12345/67890):

    Protected fixture Runtime blocks Boundary/owner matches VM instructions CFG edge matches
    AArch64 branch operations 5 5/5 27 6/6
    ARM32 VM probe 5 5/5 37 6/6
    RV64 integer operations 3 3/3 29 2/2

    The same instructions and edges are recovered when each sidecar is ignored. These counts come from the stated fixtures/seeds, not an architecture-wide coverage claim.

    The JSON emitted by quality-report --json has the stable top-level identifier "schema": "myvmp-quality-v1". Consumers should check this value before interpreting metrics; additive fields may be introduced in a future schema version. The report exits with status 1 when any requested threshold fails, so CI can treat it as a quality gate.

    Automated report bundle

    The repository includes scripts/generate_analysis_report.py:

    python3 scripts/generate_analysis_report.py \
  --tool build/myvmp \
  --input app.arm64 \
  --protected app.protected.arm64 \
  --symbol protected_calculation \
  --output build/reports/app

    It writes:

    build/reports/app/
  report.md              human-readable summary
  report.json            machine-readable index and metrics
  inspect.txt            ELF/symbol/patch plan
  lift.txt               lifted IR, when a symbol is supplied
  quality.json           before/after byte metrics, when requested
  protected.manifest.json copied sidecar, when present

    Use --before-bytes and --after-bytes to compare extracted function/payload byte ranges. Without them the script generates the other evidence but skips quality scanning. Add --whole-elf-quality only when a potentially expensive whole-file comparison is intentional; unchanged application code usually dominates that result.

    Interpreting quality metrics

    Metric Preferred direction Meaning
    same_position_ratio lower unchanged bytes at the same offset
    longest_same_position_run lower largest fixed byte island
    aligned 32/64-bit exposure lower source words found in output
    literal 32/64-bit exposure lower arbitrary source windows found in output
    pairwise ciphertext distance higher seed-to-seed payload diversity
    unique payloads/manifests equal sample count catches fixed profiles or collisions
    owner balance away from 0 both sibling VMs perform meaningful work
    bridge count non-zero proves actual cross-profile CFG transitions
    runtime/size ratio bounded operational cost

    Thresholds should be calibrated on representative protected symbols. Whole-file size ratio and similarity are usually misleading for a small protected function.

    The FunctionVmIsa API provides an experimental per-function ISA and operand grammar descriptor for specialization studies. It is metadata groundwork only; the current native encoder and runtime still use the shared bytecode operand contract.

    Project quality suites

    python3 scripts/bytecode_seed_sweep.py 16
python3 scripts/multi_vm_quality.py 8
python3 scripts/riscv64_multi_vm_quality.py 8
python3 scripts/arm64_coverage_report.py
python3 scripts/arm64_liftability_report.py
python3 scripts/riscv64_liftability_report.py

    The Makefile exposes stable wrappers for these scripts. Prefer the Make targets in automated release jobs because they build prerequisites and check generated runtime blobs.

    Recommended release evidence

    Archive the original hash, protected hash, tool hash/version, full command, seeds through a secret build record, sidecars, report bundle, behavior-test results, target compiler version and runtime/size measurements. Do not publish production seeds if they are treated as build secrets. A seed is diversity input, not a cryptographic root of trust.
